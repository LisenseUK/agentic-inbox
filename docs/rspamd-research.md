# Rspamd for agentic-inbox

Research checked 2026-10-30. This is a research and proposed design note, not a deployment record. Only this file was changed for the research. The working tree contains other ongoing work; observations describe the files inspected today. No Proxmox inventory, host capacity, network reachability or existing Redis service was assumed or inspected.

## Recommendation

Rspamd is a good fit as a self-hosted content and reputation scorer behind the existing Cloudflare receive path. Use a dedicated Debian LXC, a restricted HTTP scan proxy, Cloudflare Tunnel and an Access service token. Start with shadow scoring, then route suspicious messages to Spam. Keep unscanned mail pending and prevent agent processing until classification completes. Prefer durable R2 ingestion plus a queue for enforcement if outages must not lose mail or depend on the availability of a home server during delivery.

This will not reproduce a filter attached to the original SMTP session. Cloudflare exposes the envelope sender and recipient, headers and raw MIME, but its documented message interface does not expose a dedicated original peer IP or EHLO property. Content checks, URL/domain reputation and DKIM verification remain useful; original-IP SPF and connection reputation need trusted upstream metadata. A passing spam scan also does not make email instructions safe for an agent. [Cloudflare message API](https://developers.cloudflare.com/email-routing/email-workers/runtime-api/), [Rspamd protocol](https://docs.rspamd.com/developers/protocol/).

## What the repository does today

The integration point is [`receiveEmail`](../workers/index.ts). It checks blocked recipients, buffers `event.raw`, parses it with PostalMime, resolves the envelope recipient to a mailbox, writes decoded attachments to R2, chooses a thread and calls `createEmail(Folders.INBOX, ..., incomingEvent)`. It then schedules automatic reply drafting when enabled and Discord notifications for active mailboxes. Classification must precede those calls when enforcement is enabled. Putting a fetch in `waitUntil` after insertion would allow an MCP consumer or agent to act before the verdict.

[`workers/app.ts`](../workers/app.ts) exports the email handler and rethrows receive failures. Its comment suggests retries or bounce, but that comment is not evidence of a specific Cloudflare retry schedule. Both handlers currently narrow the event to `to`, `raw`, and `rawSize`; a future adapter needs to include `from` and `headers` to preserve envelope sender and upstream authentication results. The HTTP application's Access middleware does not authenticate this outbound scanner request; scanner Access credentials need separate configuration.

[`resolveInboundMailbox`](../workers/lib/inbound-mailbox.ts) supports catch-all delivery and provisions new mailboxes. Preserve original envelope recipient separately from the resolved storage mailbox: a catch-all mailbox is not the SMTP RCPT identity. Header To/Cc/Bcc values are not authoritative envelope recipients.

[`shared/folders.ts`](../shared/folders.ts) already defines `Folders.SPAM`; migration 2 in [`migrations.ts`](../workers/durableObject/migrations.ts) creates non-deletable `spam`. It is omitted from `SYSTEM_FOLDER_IDS` and tool-description strings. The Sidebar treats returned folders outside that system list as custom folders, so do not assume Spam is entirely invisible, but first-class navigation, recovery and tool documentation need review. [`workers/db/schema.ts`](../workers/db/schema.ts), [`workers/lib/schemas.ts`](../workers/lib/schemas.ts) and [`app/types/index.ts`](../app/types/index.ts) have no spam-verdict fields. Worker bindings are configured in [`wrangler.jsonc`](../wrangler.jsonc), supplemented by [`workers/types.ts`](../workers/types.ts); there is currently no scan endpoint or queue binding in that configuration.

R2 currently receives decoded attachments under `attachments/<messageId>/...` and mailbox/configuration records. This receive path does not persist the original `.eml`. `raw_headers` stores JSON parsed headers, not the original message. Reconstructing MIME from stored HTML and attachments will not preserve DKIM bytes or reproduce a scan. Retaining original MIME is therefore a new storage and retention decision, required for reliable rescans and useful training.

[`MailboxDO.createEmail`](../workers/durableObject/index.ts) accepts an optional incoming event and inserts the email, attachments and event delivery records within a synchronous storage transaction. [`events-store.ts`](../workers/mcp/events-store.ts) deduplicates by subscription/event ID and dispatches callbacks using alarms. The [`event protocol`](../workers/mcp/events-protocol.ts) exposes message previews but no scan verdict; the current received-event URL points to Inbox. Simply changing the folder argument would still publish an actionable `email.received` event. Enforcement should omit that event for Spam and pending mail, or introduce an explicitly designed classification-aware event contract. Keep normal accepted-mail event insertion atomic with the accepted message.

## Maintenance, licensing and scan contract

GitHub's live [latest-release API](https://api.github.com/repos/rspamd/rspamd/releases/latest) returned stable **4.2.3**, published **2026-10-21T10:54:14Z**, with `prerelease: false`. The [tagged release](https://github.com/rspamd/rspamd/releases/tag/4.2.3) includes ARC/DKIM trust, MIME parsing and networking fixes. This is direct release metadata, not a search index date or a guarantee of future support. Recheck before installation. The tagged [LICENSE.md](https://github.com/rspamd/rspamd/blob/4.2.3/LICENSE.md) is Apache-2.0. Dependency licenses and external reputation-feed terms remain separate.

Use the normal scanner on loopback port 11333. The documented v2 request is `POST /checkv2` with the complete raw MIME bytes as the HTTP body, not JSON, base64 or a PostalMime object. Example below is illustrative, with credentials omitted:

```http
POST /checkv2 HTTP/1.1
Content-Type: application/octet-stream
Accept: application/json
From: sender@example.net
Rcpt: delivery@snailbox.live
Queue-Id: <stable ingestion identifier>

<original MIME bytes>
```

`From` is SMTP MAIL FROM, including correct handling of a null reverse path; `Rcpt` is SMTP recipient. `IP`, `Helo` and `Hostname` mean original SMTP-session information and must only be supplied when verified. `User` means authenticated SMTP user, not the application's mailbox user. `Settings-ID` selects scanner policy and must be fixed by the proxy rather than controlled by email headers. HTTP metadata headers are separate from identically named MIME headers. Multiple recipients can use repeated `Rcpt` headers, but this application receives a per-recipient event; do not substitute the visible To list. Let the HTTP client set body length and test forwarding behavior. [Protocol specification](https://docs.rspamd.com/developers/protocol/), [normal worker](https://docs.rspamd.com/workers/normal/), [installation and ports](https://docs.rspamd.com/getting-started/installation/).

A successful v2 response is JSON with `is_skipped`, numeric `score`, numeric `required_score`, an `action` string and `symbols` keyed by symbol name. Symbols contain scores and optional options; optional fields include `messages`, URLs, email addresses, message ID and milter instructions. Action names contain spaces, such as `no action`, `add header`, `rewrite subject`, `soft reject`, `greylist`, and `reject`. An HTTP 200 is transport success, not a ham verdict. Validate the response shape, finite scores, skip status and recognized actions. Unknown actions or skipped scans should become an explicit indeterminate result, never implicit ham. Store a bounded result and policy/version identifier, not unlimited URLs or symbol options. [Response schema](https://docs.rspamd.com/developers/protocol/).

Recommended first client uses v2 without `body_block`, milter or zstd flags. `body_block` can append rewritten MIME after the JSON, and compression requires supported decompression. JSON parsing alone would fail on those responses. Rspamd 4.0+ also offers `/checkv3`: multipart input with a JSON metadata part and binary message part, and multipart output with a result part. It solves repeated-header encoding issues but is not a plain JSON request/response. Pin and test one protocol; avoid confusing controller `/scan` with normal-worker scanning. [v2/v3 protocol](https://docs.rspamd.com/developers/protocol/).

Proposed verdict mapping is an application policy: `no action` becomes accepted, spam marking/reject recommendations become quarantine, and temporary actions become pending/retry. Do not execute arbitrary returned milter instructions or interpret Rspamd `reject` as an automatic permanent SMTP rejection. Thresholds and forced actions can differ, so score alone is insufficient.

## LXC deployment and security boundary

Official packages currently support Debian trixie and bookworm. Use the signed stable repository with the keyring and `signed-by` configuration documented upstream, verify the installed candidate/version, and keep overrides in `/etc/rspamd/local.d/`. Rspamd can start without Redis, but upstream recommends Redis for production; Redis backs Bayes and several caching/reputation modules. Upstream explicitly documents Valkey compatibility using the same settings on EL 10. For Debian, choose the actual packaged Redis or Valkey version and test the enabled modules rather than assuming every version combination is supported. [Downloads](https://docs.rspamd.com/downloads/), [installation](https://docs.rspamd.com/getting-started/installation/), [Redis configuration](https://docs.rspamd.com/configuration/redis/).

Proposed host layout is one unprivileged Debian LXC running native systemd services for Rspamd, Redis or Valkey, Unbound, a scan-only proxy and cloudflared. No MTA, privileged container or Docker nesting is needed for this design. LXC shares the host kernel; a VM is an alternative if stronger isolation for hostile MIME parsing is required. Bind scanner, datastore and controller to loopback or Unix sockets; configure the Proxmox firewall to prevent LAN access to them. Confirm host architecture and template support before provisioning. [Proxmox container guide](https://pve.proxmox.com/pve-docs/chapter-pct.html).

Sizing is an **engineering estimate, not a measured minimum or an inventory claim**: start with 2 vCPU, 2 GiB RAM and 12–20 GiB disk without ClamAV, at low mail volume and bounded concurrency. Reserve room for Redis persistence rewrites, caches, logs and backups. Measure RSS, Redis growth, CPU and scan latency on representative messages before reducing resources or increasing concurrency. Large attachments, DNS delays and bursts matter more than daily average. No throughput claim is justified without benchmarking.

Tunnel creates outbound connections and avoids exposing an origin public IP. Put a separate scanner hostname behind an Access application with a **Service Auth** policy allowing only this scanner service token. The Worker sends `CF-Access-Client-Id` and `CF-Access-Client-Secret` from secrets on every request; rotate them and keep them out of logs. Reject redirects and unexpected content types/statuses. Tunnel is connectivity, Access is caller authentication, and the local proxy is endpoint authorization. [Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/), [service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/).

The proposed proxy accepts exactly one scan method/path, bounds request size and concurrency, imposes a deadline, and creates a fresh upstream request with allowlisted metadata. Strip client `Settings`, `Settings-ID`, `Flags`, `User`, `Password`, forwarded-IP and other Rspamd control headers; set any required policy internally. Enforce Access JWT issuer/audience/signature at the origin or through a supported cloudflared validation configuration, and ensure no alternate unauthenticated origin path exists. Access alone does not constrain which Rspamd commands an authenticated caller may invoke.

Never point the tunnel at the controller. The controller on 11334 exposes WebUI/history, learning, map/configuration changes and privileged operations such as `/learnspam`, `/learnham`, `/fuzzyadd`, `/saveactions` and `/savemap`. It can also scan, which makes exposing it tempting. Loopback is password-trusted by default, so a localhost reverse proxy can accidentally inherit administrative trust. Set distinct controller passwords, review `secure_ip`, and keep management/learning on an operator-only path outside the scan hostname. No scanner service credential should authorize learning. [Controller configuration and commands](https://docs.rspamd.com/workers/controller/).

## SMTP identity and authentication trust

Cloudflare's current documentation says it validates DMARC before invocation and prepends `Authentication-Results`. Trust the first such header only after checking its authentication service identifier is `mx.cloudflare.net`; other copies can be supplied by a sender. Cloudflare says ARC verification is unnecessary for trusting this directly invoked Worker result. Parse the syntax and duplicate headers correctly, not a substring search across all header values. Preserve the extracted result and its Cloudflare-ingress provenance as separate metadata across R2/queue processing. Do not assume any header merely claiming `mx.cloudflare.net` is trusted in an uploaded test message or a public scan API. [Cloudflare authentication results](https://developers.cloudflare.com/email-routing/email-workers/runtime-api/).

The HTTP peer seen by Rspamd is the proxy/tunnel, not the SMTP sender. `CF-Connecting-IP` describes an HTTP connection, not the original mail connection. Never use it for SPF. Likewise, do not mark all proxied mail as authenticated/local or broadly whitelist Cloudflare IPs, since that can bypass checks. A trusted, documented Received boundary could support deriving original metadata, but arbitrary Received lines are forgeable. Rspamd's [external relay module](https://docs.rspamd.com/modules/external_relay/) is relevant only once trusted relay boundaries are established and tested; it cannot manufacture missing session facts.

DKIM can be reverified from intact MIME and DNS, subject to any upstream transformations and later key changes. SPF requires the original connecting IP and envelope/HELO identity; absent that IP, disable or neutralize inappropriate connection-based checks in the scanner profile and use the trusted upstream authentication outcome. DMARC's SPF branch inherits that limitation. Propose explicit local symbols or application policy based on the vetted Cloudflare result, not globally trusting all `Authentication-Results` headers. Acceptance testing must inspect effective symbols and scores to detect SPF/DMARC double counting. [SPF module](https://docs.rspamd.com/modules/spf/), [DKIM module](https://docs.rspamd.com/modules/dkim/), [DMARC module](https://docs.rspamd.com/modules/dmarc/).

## DNS, training and retained data

Use an explicitly configured local recursive resolver such as Unbound, with working UDP/TCP DNS egress. Major blocklists refuse shared public resolvers such as 1.1.1.1 and 8.8.8.8; Spamhaus refusal can produce `RBL_SPAMHAUS_BLOCKED_OPENRESOLVER`. This is degraded coverage, not evidence the message is clean. Monitor resolver failures, blocked-list symbols and list health. A public-resolver fallback can silently restore this problem. [Rspamd installation DNS guidance](https://docs.rspamd.com/getting-started/installation/), [RBL module](https://docs.rspamd.com/modules/rbl/).

A recursive resolver does not grant a feed license. Inventory each enabled DNSBL, URL list and fuzzy provider; check its operator's commercial-use, attribution, volume and resolver requirements. This project's commercial/multiservice context means free-use eligibility must be established, not inferred from small volume or open-source Rspamd. Budget a subscription or disable ineligible checks. Spamhaus's [fair-use policy](https://www.spamhaus.org/blocklists/dnsbl-fair-use-policy/) needs operator review before enabling its free service here; direct retrieval was blocked during this research, so no numeric entitlement is asserted.

Rspamd has useful nonstatistical rules before training. Bayes needs labeled spam and ham; the 4.2.3 default configuration sets Redis backend, `min_tokens = 11` and `min_learns = 200`. Plan at least 200 eligible distinct examples of each class and verify counters/classification in the effective configuration. Tiny, duplicate or rejected learning submissions may not count. Do not lower the threshold merely to make Bayes activate. [Tagged statistic defaults](https://github.com/rspamd/rspamd/blob/4.2.3/conf/statistic.conf), [statistics configuration](https://docs.rspamd.com/configuration/statistic/), [first setup](https://docs.rspamd.com/getting-started/first-setup/).

Proposed initial training is operator-reviewed, with raw MIME and a recorded label source. Keep a held-out corpus for evaluation. Do not treat Inbox delivery or arbitrary folder moves as ground truth; automatic self-training can reinforce false positives and allow poisoning. Defer autolearning and neural models until labels and recovery are reliable. Decide whether Bayes is global or per mailbox; global training shares signals across tenants, while sparse individual mailboxes may never reach useful sample counts. A folder move alone does not currently train anything in this repository.

Persist `/etc/rspamd`, `/var/lib/rspamd`, datastore files and secrets through the chosen backup mechanism. Configure and test Redis/Valkey persistence rather than assuming the package default is adequate. Separate disposable caches from irreplaceable learned data where eviction policy would otherwise discard training. Restore-test classifier counts, configuration, policy identity and scan behavior. Proxmox bind mounts and additional volumes need explicit backup treatment; a container backup alone should not be assumed to include every mount. Raw-message retention, quarantine deletion and backup expiry should follow one documented policy. [Rspamd administration FAQ](https://docs.rspamd.com/faq/), [Proxmox storage and backups](https://pve.proxmox.com/pve-docs/chapter-pct.html).

ClamAV is optional and separate from spam scoring. Rspamd's antivirus module supports local ClamAV INSTREAM scans, configurable size/time limits, virus and failure symbols, and encrypted/macro signals. It needs clamd and updated signatures; a timeout, oversized file or encrypted archive is not a clean scan. Make malware policy explicit and verify which MIME parts are scanned. Start without it unless attachment malware scanning is a requirement. **Sizing estimate with ClamAV:** consider 4–6 GiB total RAM and more disk, then benchmark signature reloads and simultaneous scans. [Antivirus module](https://docs.rspamd.com/modules/antivirus/).

## Failure policy and durable ingestion

For an initial synchronous experiment, scan buffered MIME before decoded attachment writes and message creation, with a bounded deadline shorter than the platform budget. Abort slow requests and retry only bounded transient failures. Network failures, Access denial, invalid JSON, skipped scans, missing mandatory results and DNS/AV failures must be observable and distinct from ham. A content scan may return HTTP 200 while an individual module failed, so inspect relevant error symbols too. Verify current [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [email limits](https://developers.cloudflare.com/email-routing/limits/) before choosing deadlines or maximum message size.

Proposed enforcement fails closed for automation but preserves delivery: pending mail waits for a scan, with an operator-visible backlog and explicit release path. A fail-open option could deliver visibly marked mail during an outage, but must still disable drafts, notifications carrying content and normal MCP received events until policy allows them. Shadow mode may retain existing delivery behavior, clearly understood to provide no blocking protection. Permanent SMTP rejection is a later decision because false positives cannot be recovered locally, and asynchronous processing cannot undo SMTP acceptance. Do not generate backscatter bounces after acceptance.

For durable processing, propose:

1. Validate recipient/block policy, allocate a stable ingestion ID, and await storage of original MIME in private R2 with an envelope/provenance manifest and a durable pending record. Recheck mailbox blocks before final delivery.
2. Await enqueue of a small job containing the ingestion ID and R2 key, not MIME. Return only after durable ingestion succeeds. R2 and queue writes are not one transaction, so reconcile orphaned raw objects and pending records when enqueue fails.
3. A consumer fetches MIME, calls the scan proxy, records verdict/status/version and retries transient failures with backoff. Use a dead-letter queue plus reconciliation and alerts for exhausted or expired work.
4. On accepted classification, create the message/attachments and accepted-mail event atomically where possible, then dispatch idempotent draft/notification jobs. On spam classification, create it in Spam without the ordinary event or draft. On indeterminate classification, keep it pending. Do not insert Inbox first and move later.
5. Use the stable ingestion ID for uniqueness, event ID and each downstream effect. Queue redelivery must not repeat attachment writes, draft generation or notifications. A MIME hash alone is not a sufficient identity for deliberate repeat deliveries; define SMTP-redelivery deduplication separately. Use an outbox/completion state for crashes between database commit and downstream side effects.

Queues provide at-least-once delivery, so duplicate handling is required. Queue retention is finite and dead-letter storage also needs operational handling; a reconciler should be able to reconstruct unfinished work from durable pending records. `waitUntil` is not the durable queue. This design requires new raw storage, state schema, consumer code and bindings; none exist in the inspected receive implementation. [Delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), [queue retry behavior](https://developers.cloudflare.com/queues/configuration/batching-retries/).

## Privacy and operating costs

Self-hosting avoids sending full mail to a commercial spam-scoring API, but MIME still travels through Cloudflare and the tunnel into the LXC. DNS queries expose queried domains/IPs to recursive infrastructure and list operators; fuzzy checks and optional external modules send their respective data. Audit enabled modules, especially GPT, external services, URL fetchers, fuzzy storage and commercial scanners. Keep GPT/full-content exports off unless separately authorized. Block scans from reaching LAN/link-local services through URL fetching, and bound archive decompression and resource use. Keep R2 private, avoid body/header dumps in logs, limit history and encrypt protected backups. Existing Discord notifications already send previews externally; quarantine and pending messages should not trigger them. [Rspamd modules](https://docs.rspamd.com/modules/), [antivirus external lookups](https://docs.rspamd.com/modules/antivirus/), repository receive path above.

Rspamd has no per-message software license fee under Apache-2.0. Actual cost includes host capacity, power, storage/backups, maintenance, Cloudflare plan/compute, and any paid reputation feeds. Existing server capacity and Cloudflare entitlements are unknown. Do not quote the LXC as free or assume Access availability implies a zero incremental bill.

At retrieval, Standard R2 storage is $0.015/GB-month with $4.50/million Class A and $0.36/million Class B operations, free Internet egress, and an applicable free tier. Paid Queues includes one million operations/month, then $0.40/million; a normal delivery generally uses write, read and delete, with additional reads on retries and 64 KiB chunk accounting. Free Queues has different daily limits and retention. Worker/DO compute and existing usage are additional. These are USD list prices, not an account quote. [R2 pricing](https://developers.cloudflare.com/r2/pricing/), [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/).

**Illustrative storage estimate:** 10,000 messages/month averaging 250 KB is roughly 2.5 GB of raw mail retained for one month, before separately stored attachments, quarantine, manifests, scan results, logs and backups. Base queue delivery is roughly 30,000 small-message operations before retries. That can fit published allowances only if the account has allowance remaining. Measure actual MIME sizes and retention before forecasting spend.

## Rollout, acceptance criteria and open questions

First build an isolated scanner configuration and replay a redacted or authorized labeled corpus. Verify configuration with `rspamadm configtest` and inspect `configdump`; confirm installed release, ports, DNS behavior and persistence. Test normal mail, GTUBE spam, forwarded mailing lists, null envelope senders, Bcc/catch-all delivery, duplicate/forged authentication headers, broken DKIM, DNS outages, long scans, malformed MIME, large attachments and AV failures if enabled. GTUBE confirms plumbing, not real-world accuracy. Use a held-out corpus for false-positive rate and detection measurements. [Rspamd first setup](https://docs.rspamd.com/getting-started/first-setup/).

Then run shadow scoring on representative production traffic. Measure scan p50/p95/p99, end-to-end delay, error/skip rates, symbol coverage, Redis growth and false positives by mail category. Record policy version so an upgrade can be compared and rolled back. Shadow scanning on a sample is useful for cost/latency evidence but does not prove full-load capacity.

Enable quarantine for a limited cohort only after operators can inspect and release Spam and pending mail. Test that those messages produce zero premature drafts, accepted-mail MCP callbacks or Discord previews. Simulate failure after every ingestion/queue/scan/commit boundary, duplicate queue deliveries, token expiry, tunnel outage, restoration from backup and redelivery after recovery. Rollback must stop enforcement or restore the prior policy without losing pending objects or flooding agents with replayed events. Expanding to permanent rejection should require measured false-positive performance and a separate retention/recovery decision.

Questions to settle before implementation:

- What are peak concurrent deliveries, maximum MIME size, desired delivery latency and tolerated pending time?
- Which Proxmox node/storage has capacity, what are the host architecture and backup arrangements, and is a VM preferable to LXC for this workload?
- Is original-MIME retention acceptable, for how long, and who may view quarantine, release mail or train the model?
- Can the scanner use a local recursive resolver with unrestricted necessary DNS egress, and which feed licenses cover this service?
- Should upstream authentication failures quarantine immediately, or contribute bounded score alongside content checks? Can any original SMTP IP/EHLO be extracted through a verified Cloudflare boundary?
- Should MCP ever expose quarantined-mail events, and what is the release-event contract? How should released mail trigger drafts without duplicates?
- Is ClamAV required, and how should encrypted/oversized/unscannable attachments be handled?
- Which Cloudflare plan, shared allowances, token policies, queue retention and operational on-call arrangements actually apply?

No deployment or application changes are part of this research.
